01 / what_is_burp.txt

What is Burp Suite?

Burp Suite provides tools for analyzing web applications. Its proxy-based workflow lets a tester observe communication between a browser and an application, making it easier to understand how the application handles input, sessions, cookies, and responses.

Made by PortSwigger, Burp Suite comes in a free Community Edition and a paid Professional Edition with automated scanning and extra tooling. Most learners start with the Community Edition — the core skill it teaches, reading and reasoning about raw HTTP traffic, doesn't require the paid features.

Because Burp sits as a proxy between your browser and the target application, it can only show you what your own browser is already sending and receiving. That is an important distinction from a network scanner: Burp doesn't "attack" anything by itself — it makes visible, and lets you deliberately resend, traffic that already exists.

diagram · proxy_flow.svg

Burp sits in the middle of a request you already initiated, letting you pause, inspect, and optionally edit it before it reaches the server.

02 / core_components.txt

Core Components

Proxy helps inspect HTTP traffic; Repeater lets you resend and study individual requests; Intruder supports controlled automated testing; Decoder helps transform encoded data; Comparer helps compare messages and responses; Target/Site map organizes everything you've observed into a navigable tree; and the Logger records every request and response for later review.

[+] Proxy — intercepts and displays live HTTP traffic

[+] Repeater — resend and tweak a single request by hand

[+] Intruder — automates sending many variations of a request

[+] Decoder — encode/decode Base64, URL, HTML entities, and more

[+] Comparer — diff two requests or responses side by side

[+] Target/Site map — builds a picture of the whole application

[+] Logger — a searchable history of everything observed

[+] Extender — adds community-built extensions (Professional/BApp Store)

03 / how_web_testing_works.txt

How Web Testing Works

A browser sends an HTTP request containing a method, URL, headers, cookies, and possibly a body. The server processes that request and returns a response. A tester can inspect this exchange to understand application behavior and identify security weaknesses.

Sessions and authentication are usually built on top of this simple request/response pattern using a cookie or token that the browser automatically re-sends with every request. Understanding exactly what value proves "who you are" to the server — and where that value lives — is one of the most useful skills Burp practice builds, because so many web application weaknesses ultimately come down to that value being predictable, stealable, or not checked properly.

04 / reading_requests.txt

Reading HTTP Requests

Pay attention to the request method, path, query parameters, headers, cookies, content type, and body. Understanding these parts is more important than memorizing Burp buttons.

example_request.txt
GET /account/profile?id=482 HTTP/1.1
Host: lab.local
Cookie: session=8f2c...
User-Agent: Mozilla/5.0
Accept: text/html

> Method: GET   Path: /account/profile   Param: id=482
> Ask yourself: what happens if id were a different number? Does the server check that it belongs to the logged-in session?
05 / safe_examples.txt

Safe Lab Examples

Use Burp against an application you own or a training target such as a deliberately vulnerable local lab. A beginner exercise is to open a local test application through the proxy, capture a normal request, inspect its parameters, and resend the same request without changing anything.

Once resending an unmodified request feels comfortable, try Repeater on a request with a numeric ID or a query parameter and change only that value, then compare the new response in Comparer. This teaches you how to read the effect of a single change in isolation — the core habit behind almost all web application testing.

06 / practical_lab.txt

Practical Lab

Set up a local training web application, configure a browser to use Burp's proxy, browse the application, capture requests, identify authentication-related values, and document how different pages communicate with the server.

1

Install a local, intentionally vulnerable training application designed for learners, and run it only on your own machine or an isolated lab VM.

2

Point your browser at Burp's proxy and install Burp's CA certificate so HTTPS traffic can be inspected in your lab browser.

3

Log in normally and browse a few pages, letting Burp's Proxy history and Site map fill in.

4

Find the request that carries your session cookie and note every page that reuses it.

5

Send one interesting request to Repeater, change one parameter at a time, and document how the response changes.

07 / defensive_view.txt

Defensive Perspective

The same observations help developers secure applications. Validate input on the server, use secure session handling, apply authorization checks to every sensitive operation, protect cookies, and avoid trusting client-controlled values.

Practical defensive habits include marking cookies HttpOnly and Secure, checking on every request that the logged-in user is actually allowed to access the specific record being requested (not just that they're logged in at all), rotating session identifiers after login, and never relying on a hidden form field or client-side check as the only line of defense.

08 / ethics_and_law.txt

Ethics & Legal Considerations

Intercepting and modifying traffic to a web application you do not own or have written permission to test can violate computer-misuse laws and a site's terms of service, even if no damage occurs. Keep Burp pointed at your own applications, dedicated training labs, or programs that explicitly invite testing (such as a scoped bug-bounty program), and stay within whatever rules that program sets.

Capturing traffic that contains other people's real data — even by accident on a shared network — raises privacy concerns beyond authorization. Practice on isolated, single-user lab environments.
09 / learning_roadmap.txt

Learning Roadmap

Learn HTTP → learn HTML forms and APIs → understand cookies and sessions → learn Burp Proxy → practice Repeater → study authentication and authorization → study common web vulnerabilities in legal labs.

1

HTTP fundamentals — methods, status codes, headers.

2

HTML forms & APIs — how a browser turns a user action into a request.

3

Cookies & sessions — how an application remembers who you are.

4

Burp Proxy fundamentals — intercepting your own traffic.

5

Repeater practice — controlled, one-change-at-a-time experiments.

6

Authentication & authorization concepts — proving who you are vs. what you're allowed to do.

7

Common web-application weakness categories, studied in legal, structured labs.
