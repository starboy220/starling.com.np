01 / what_is_wireshark.txt

What is Wireshark?

Wireshark captures packets from a network interface and presents protocol information in a human-readable form. It can help you understand how applications communicate and diagnose unusual network behavior.

Wireshark began life as "Ethereal" in 1998 and is now one of the most widely used open-source network analyzers in the world, relied on by network engineers, incident responders, and students alike. It works by putting a network interface into a mode where it can see traffic passing by, then decoding each layer of that traffic using its huge library of built-in protocol dissectors.

A useful mental model: a scanner like Nmap asks active questions and records the answers, while Wireshark passively watches whatever traffic is already flowing and reconstructs the conversation after the fact.

diagram · protocol_layers.svg

Each captured frame is a stack of these layers wrapped inside one another. Wireshark's packet-detail pane mirrors this stack, letting you expand each layer independently.

02 / packet_structure.txt

Understanding Packets

A packet can contain multiple protocol layers. Ethernet or another link layer carries IP, IP carries TCP or UDP, and application protocols such as DNS or HTTP may sit above them. The exact stack depends on the traffic.

In Wireshark's packet list, each row is one frame; the packet-detail pane below it lets you expand each layer — Frame, Ethernet, IP, TCP/UDP, and finally the application protocol — to see the individual fields Wireshark decoded. The bottom hex pane shows the same data as raw bytes, which is useful once you want to understand exactly how a protocol is structured on the wire.

04 / filters.txt

Display Filters

Display filters help narrow a capture. Examples for a personal lab include dns, http, tcp, and ip.addr == 127.0.0.1. These filters select packets for viewing; they do not change the captured traffic.

It's worth knowing the difference between a capture filter (set before you start capturing, using a more limited syntax, and it determines what gets recorded at all) and a display filter (applied after the fact, using Wireshark's richer syntax, and it only changes what you currently see — nothing already captured is discarded). A few more display-filter examples worth trying on your own lab captures: tcp.port == 443, http.request, and tcp.flags.syn == 1 to isolate connection attempts.

05 / safe_examples.txt

Safe Lab Examples

Capture traffic generated by your own browser or a local application. Start a capture on the correct interface, visit a local test site, stop the capture, and inspect the DNS, TCP, and application-level exchanges.

A good first exercise: capture while visiting a single local site, then use Wireshark's "Follow → TCP Stream" feature on one connection to see the request/response exchange reassembled as readable text. This makes the abstract idea of "a TCP connection" concrete.

06 / practical_lab.txt

Practical Lab

Capture a short session, identify DNS queries, follow a TCP conversation, locate the client and server addresses, and note which protocols are visible. Repeat the exercise with encrypted HTTPS traffic and compare what information remains observable.

1

Start a capture, then generate a small, predictable amount of traffic — a couple of page loads or a ping.

2

Filter to dns and note every name your machine looked up, including ones you didn't expect.

3

Filter to one TCP conversation and use Follow → TCP Stream to read the whole exchange.

4

Repeat the capture against an HTTPS site and compare — you'll still see the handshake and metadata, but not the encrypted payload.

5

Write down, in your own words, what an observer on the network path could and couldn't learn from each capture.

07 / defensive_view.txt

Defensive Perspective

Packet analysis can reveal misconfigurations, unexpected connections, protocol misuse, and signs of compromise. Encryption protects application content, but metadata such as endpoints and timing can still provide useful information.

Defenders often build a baseline of "normal" traffic for a network segment so that anomalies — an internal machine suddenly talking to an unfamiliar address, an unexpected protocol on a well-known port, or a burst of DNS lookups to newly registered domains — stand out. Packet captures are also a core piece of evidence during incident response, which is why many organizations retain them for a defined period.

08 / ethics_and_law.txt

Ethics & Legal Considerations

Capturing network traffic that belongs to other people — for example, on a shared Wi-Fi network you don't administer, or a corporate network without authorization — can violate wiretap, privacy, or computer-misuse laws even if you never act on what you see. Only capture traffic on networks and devices you own, administer, or have explicit written permission to monitor.

Even in an authorized capture, avoid storing more sensitive data than your exercise needs, and delete lab captures once you're done with them.
