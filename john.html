01 / what_is_john.txt

What is John the Ripper?

John the Ripper is designed to test password strength by working with password hashes and candidate passwords. Security teams can use controlled password audits to identify weak credentials before attackers do.

First released in the late 1990s, John the Ripper was built to help system administrators find weak passwords on their own systems before someone else did. It supports many different hash formats so an auditor can point it at whatever scheme a given system actually uses, rather than assuming one format fits all.

diagram · hash_check_flow.svg

Because hashing is one-way, an auditor can never "decrypt" a hash back into a password — the only way to check a guess is to hash it the same way and compare the result.

02 / hashing_vs_encryption.txt

Hashing Is Not Encryption

A password hash is intended to be a one-way representation rather than a reversible encrypted password. A password auditor attempts candidate values, hashes them using the appropriate scheme, and checks whether the result matches the stored hash.

There are a few broad strategies for choosing candidate values: a dictionary attack tries words from a wordlist; a rule-based attack takes those words and applies common human patterns to them (capitalizing the first letter, appending a digit, and so on); and a brute-force attack tries every possible combination up to a given length, which becomes impractical very quickly as length grows. This is exactly why longer, more random passwords resist auditing (and real attacks) so much better than short, pattern-based ones.

03 / audit_concepts.txt

Password Audit Concepts

Important ideas include password length, uniqueness, dictionaries, password reuse, salts, key-derivation functions, rate limits, and multi-factor authentication. Modern password storage should use dedicated password-hashing/KDF schemes rather than fast general-purpose hashes.

A salt is random data mixed into a password before hashing, unique per account, so that two users with the same password end up with different stored hashes — this defeats precomputed lookup tables. Dedicated password-hashing algorithms are deliberately slow and memory-intensive (unlike fast general-purpose hashes originally designed for things like file integrity checks), which raises the cost of testing large numbers of guesses even for someone with legitimate access to the hash database.

04 / safe_examples.txt

Safe Lab Examples

Use only hashes created specifically for your own lab. A useful exercise is to generate test accounts with deliberately weak and strong passwords, store them using an appropriate password-hashing library, and compare how password policy affects audit results.

Try creating five test accounts with passwords of increasing complexity — a common word, a common word with a digit appended, a short random string, a long random string, and a long random passphrase — then time how the audit results differ across them. The gap between the "common word" and "long random passphrase" rows is usually the most convincing password-policy argument you'll ever see.

05 / practical_lab.txt

Practical Lab

Create a small local password-audit dataset containing dummy credentials. Document the hashing scheme, test only the dummy hashes, record which test passwords were weak, and then improve the password policy.

1

Create a handful of dummy accounts with a deliberate mix of weak and strong passwords — never real credentials.

2

Hash them with a modern, salted password-hashing scheme and record which scheme you used.

3

Run a dictionary-based audit against only your dummy hash file.

4

Record which passwords were recovered quickly, which resisted the audit, and why.

5

Write a one-paragraph password policy recommendation based on what you observed.

06 / defensive_view.txt

Defensive Perspective

Defenders should use strong password policies, unique passwords, secure password hashing with salts and suitable work factors, MFA where appropriate, monitoring, and protections against online guessing.

"Online" guessing (repeatedly trying to log in through the application itself) and "offline" auditing (testing a stolen or leaked hash database) call for different defenses. Rate limiting, account lockout, and CAPTCHA-style friction address online guessing; strong hashing algorithms, salts, and adequate work factors address offline auditing. A defense-in-depth password strategy needs both, plus multi-factor authentication as a backstop when a password is compromised anyway.

07 / ethics_and_law.txt

Ethics & Legal Considerations

Only ever run a password audit against hash databases you own or have explicit written authorization to test — for example, as part of your own organization's authorized security program. Testing credentials that belong to real people without permission, even ones you found publicly leaked, can violate computer-misuse and privacy laws.

Never test real user credentials, even from your own production systems, outside of a formally authorized audit with clear data-handling rules.
