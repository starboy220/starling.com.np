01 / what_is_nmap.txt

What is Nmap?

Nmap ("Network Mapper") is a free, open-source utility originally released in 1997 by Gordon Lyon. It helps security professionals and administrators understand what systems are reachable and which network services they expose. It is commonly used for inventory, troubleshooting, security auditing, and controlled penetration-testing labs.

Because Nmap simply sends and interprets standard network traffic, it is considered a "dual-use" tool: the exact same scan that helps a system administrator confirm a firewall rule is working can also be used by an attacker to look for a way in. This is why every guide on this page repeats the same rule — only point Nmap at systems you own or are explicitly authorized to test.

Nmap ships with a companion scripting engine (NSE), a version-detection database, and a GUI front-end called Zenmap. Most learners start with the command-line tool because the flags map directly onto networking concepts you already know from TCP/IP fundamentals.

02 / how_it_works.txt

How Nmap Works

A scanner sends carefully constructed network probes and observes responses. From those responses, Nmap can determine whether a host is reachable, whether ports appear open or closed, and sometimes which service or operating system is associated with the target.

At a conceptual level, Nmap's workflow has four stages: host discovery (is anything answering at this address?), port scanning (which of the 65,535 TCP/UDP ports respond?), service/version detection (what software is listening, and which version?), and optionally OS fingerprinting (what does the pattern of responses suggest about the operating system?). Each stage builds on the last, which is why a full scan takes longer than a quick ping sweep.

Different scan types simply change how the initial probe is built. A TCP connect scan completes a full handshake through the operating system's own networking stack, which is reliable but easy to log. Understanding the handshake itself is the real learning goal — the scan type is just a different way of asking the same three questions: is it open, closed, or filtered?

Simplified view of the TCP three-way handshake Nmap's connect-style scanning relies on. This is the same handshake every normal TCP connection uses — Nmap just automates asking the question at scale.

03 / common_uses.txt

Common Uses

Host discovery; TCP/UDP port discovery; service and version identification; basic OS detection; network inventory; troubleshooting unexpected exposure; change-detection between two scans of the same authorized network; and validating that a firewall rule actually blocks what it's supposed to.

04 / reading_output.txt

Reading Nmap Output

A typical result can show a port number, protocol, state, and service. An open port generally means an application is accepting connections. A closed port responds but is not accepting an application connection. Filtered means a firewall or other network control prevents Nmap from determining the state with confidence. You may also see open|filtered or closed|filtered, which mean Nmap received no response at all and cannot distinguish between the two possibilities — this is common with UDP scanning, where silence is ambiguous.

example_output.txt
PORT STATE SERVICE VERSION
22/tcp open ssh OpenSSH
80/tcp open http nginx
123/udp open|filtered ntp
445/tcp filtered microsoft-ds
3306/tcp closed mysql

> Read results as evidence to investigate, not as automatic proof of compromise.
> A version string is a clue, not a confirmed vulnerability — always cross-check against a trusted advisory before drawing conclusions.
05 / safe_examples.txt

Safe Lab Examples

Practice only against your own computer, a deliberately vulnerable lab, or another system where you have explicit permission. For example, scanning your own machine with nmap localhost is a simple way to see locally exposed TCP services. You can compare the result with the services you intentionally started.

A few more beginner-friendly, self-directed examples to try only against your own machine or lab VM: nmap -sV localhost to add version detection to the results you already saw, nmap -p 1-1000 127.0.0.1 to limit the scan to the first thousand ports, and nmap --top-ports 20 localhost to check only the twenty most commonly used ports. Comparing the output of each command helps you understand what each flag actually changes.

06 / practical_lab.txt

Practical Lab

Create a small virtual-machine lab. Identify the lab machine's address, run a basic authorized scan, record discovered ports, identify the services responsible, and decide whether every exposed service is actually needed.

1

Spin up two virtual machines on an isolated, host-only network — one acting as the "target," one as the "scanner." Confirm neither can reach the public internet or your production network.

2

On the target VM, note which services you intentionally started (for example, a local web server or SSH daemon) so you have a known answer key.

3

From the scanner VM, run a basic scan against the target's private IP address and record every open port and reported service.

4

Compare the scan results to your answer key. Investigate any surprises — an unexpected open port is exactly the kind of finding a real audit is looking for.

5

Disable one unnecessary service on the target, re-scan, and confirm the port disappears from the results. This closes the loop between finding and fixing.

07 / defensive_view.txt

Defensive Perspective

Nmap results are valuable to defenders because they reveal attack surface. Unnecessary services should be disabled, exposed services should be patched, and network segmentation and firewall rules should limit access where appropriate.

Many organizations run their own authorized scans on a schedule so they see their exposure before an outsider does. Pairing scan results with an asset inventory helps answer the most important defensive question: "does every open port map to a service we actually intend to expose, to the people who actually need it?" Logging and alerting on scan-like traffic patterns can also help defenders notice reconnaissance activity against systems they monitor.

08 / ethics_and_law.txt

Ethics & Legal Considerations

In most jurisdictions, scanning a system without the owner's permission can be a civil or criminal matter, regardless of intent. Before running Nmap against anything other than your own equipment or a dedicated lab, make sure you have clear, written authorization that states which systems, time windows, and scan types are permitted.

If you are ever unsure whether you're authorized to scan something, the safe default is: don't. Ask first, or stay inside your own lab.
